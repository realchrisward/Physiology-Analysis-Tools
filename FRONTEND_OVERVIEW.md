on the `web-ui-redesign` branch. Update this as later milestones land, the
same way `BACKEND_OVERVIEW.md` tracks the (now complete) backend. Full

## Files

| File | Purpose |
|---|---|
| `frontend/src/lib/api.ts` | `getBackendUrl()` — resolves the real backend port via Electron IPC (`window.api.getBackendPort`), falls back to `http://127.0.0.1:8000` outside Electron. |
| `frontend/src/lib/api/http.ts` | `apiGet`/`apiPost` — shared fetch wrapper. Never throws: network failures and non-2xx responses are caught and returned as `{status:'error', error}`. |
| `frontend/src/lib/api/types.ts` | Hand-written TS interfaces mirroring every `backend/models.py` class the client uses, plus `ApiError` (the explicit failure-shape union member for the 3 endpoints whose success shape doesn't carry `status`/`error`). |
| `frontend/src/lib/api/{files,beats,arrhythmia,settings,windowing,persistence}.ts` | One thin wrapper file per backend router, all 15 endpoints. |
| `frontend/src/lib/tokens.css` | Design tokens: color (neutral scale + accent + semantic success/warning/danger, WCAG AA, light+dark), spacing, type (incl. a mono scale for numeric readouts), radii, shadow. |
| `desktop/main.js` | Electron main process. Spawns/tears down the backend subprocess; `ipcMain.handle`s: `get-backend-port`, `pick-files`, `pick-folder`, `pick-output-directory` (all dialog-based, filtered to `SUPPORTED_EXTENSIONS` — `adicht`, `txt`, `mat`, `gzip`, `edf`). |
| `desktop/preload.js` | `contextBridge.exposeInMainWorld('api', {...})` — the only surface the renderer can call into Electron/Node through. |
| `frontend/src/components/import/ImportScreen.svelte` | The app's first real screen (replaces the `HealthStatus` scaffold demo in `App.svelte`). File/folder import (native pickers), per-file status with error isolation, "Auto-run beat detection" (checked by default, sequential, learned ETA via `eta.ts`), Stop (drains the queue, lets the in-flight file finish). |
| `frontend/src/lib/stores/eta.ts` | `recordSample(bytes, seconds)`/`estimate(bytes)` — session-scoped running bytes/sec average. `estimate` returns `null` until at least one real sample exists (the "Calculating…" case) — never a fabricated hardcoded guess presented as real. |
| `frontend/src/App.svelte` | App shell — `view: 'import'\|'review'` switch (deferred here from F1/F2's own scope rulings). Renders `ImportScreen` or `ReviewWorkspace`. |
| `frontend/src/components/review/ReviewWorkspace.svelte` | Channel selection (`selectedChannel` drives the `<select>`; a separate `activeChannel` only advances once `detectBeats()` resolves successfully for the new channel — see Design decisions), detection summary, hosts `EcgGraph`. |
| `frontend/src/components/graph/EcgGraph.svelte` | The ECG graph — `uplot` wrapper (first real npm runtime dependency, pinned exact `1.6.31`). Real pan (drag)/zoom (wheel) against `GET /channels/window`, debounced 150ms; Reset View restores the real full extent from the initial load. Beat/arrhythmia markers from `GET /beats/window` (3 visual categories: flagged/normal/not-yet-evaluated) via a testable `buildBeatAlignedData` seam. "Mark Bad Data" mode toggles drag behavior to add (`POST /files/bad-data`) instead of pan; clicking an existing mark removes it (`DELETE /files/bad-data`). Marks render as a proportional strip below the graph (known limitation, see below). |

## Design decisions

- **No UI framework, no router, no state-management library** — plain CSS + design tokens, Svelte 5 runes for state, a small number of named views driven by simple component state (an offline desktop tool has no shareable-URL/deep-linking need).
- **Charting: `uplot`** (arrives in F3) — chosen for large time-series + pan/zoom + tiny footprint, matching the ECG graph's real requirements (see the frontend design spec for the full rationale).
- **API client never throws** — every function resolves to a value; callers check `.status`/narrow via `'error' in result`, mirroring the backend's own "never surprise the caller" convention. `SUPPORTED_EXTENSIONS` (`desktop/main.js`) is the single source of truth for supported file types on the Electron side — kept in sync with `backend/extractors.py`'s `EXTRACTOR_SPECS` by inspection (no shared source between the two processes; a real, if narrow, drift risk — noted below).
- **3 of the 15 API client functions have a `T | ApiError` return type**, not a bare `T` — `importFiles` (`ImportResponse`), `listFiles` (`FileImportResult[]`), `getSettings` (`SettingsPayload`) — because their success shapes don't naturally carry `status`/`error`, unlike the other 12. Any future endpoint wrapper whose success type also lacks those fields needs the same treatment; check before assuming the bare cast is safe.
- **A screen with a cancelable async batch operation needs ONE state value covering the ENTIRE operation, set synchronously before the first `await`** — not multiple flags set at different points in the flow. `ImportScreen`'s auto-run queue went through two fix rounds before landing on this: the first attempt (`queueRunning`, set only once beat-detection started) left the native-picker and import-network phases unguarded, letting a double-click spawn two concurrent queues. The fix: `queueState: 'idle'|'busy'|'stopping'`, set to `'busy'` as the literal first statement of the click handler (before awaiting the picker), reset via one `finally` covering every exit path. F4's arrhythmia re-run (heuristic/unsupervised/both, with progress feedback) will face the exact same shape of problem — reuse this pattern from the start rather than re-deriving it.
- **A component that unmounts (or remounts via `{#key}`) must tear down ANY `document`-level event listener it attached itself**, not just rely on its own cleanup of its own DOM subtree — `chart.destroy()` (uPlot) or an equivalent library teardown does not know about listeners YOUR code attached to `document`. `EcgGraph`'s drag-to-pan and drag-to-mark-bad-data both attach `document`-level `mousemove`/`mouseup` (needed so a drag continues tracking even if the cursor leaves the plot area mid-drag) — this leaked on unmount through two real bug rounds before landing on a single `endActiveDrag` teardown slot, set by whichever drag started, called unconditionally from the component's unmount cleanup BEFORE the library's own destroy. Any future custom drag/global-listener interaction in this codebase should use this exact pattern from the start.
- **A value change that drives BOTH a slow, awaited side effect AND an immediately-observable UI element (e.g. a component remount) must not let the immediate path race ahead of the slow one.** `ReviewWorkspace`'s channel `<select>` triggers both a real `detectBeats()` computation AND (via `{#key}`) an immediate graph remount that independently re-fetches beat data from a backend cache the slow call is what's supposed to update first. Fixed by splitting the bound/displayed value (`selectedChannel`) from the value that actually drives the remount (`activeChannel`), advancing the latter only after the slow operation resolves successfully — plus a request-id guard against a stale, superseded response reordering things if the value changes again before the first request finishes. Any future "changing X should both re-run a backend computation AND refresh a dependent view" interaction needs this same two-variable-plus-request-id shape, not a single shared value.
- **A test asserting "no fetch happened yet" or "state unchanged" around something debounced/delayed must actually advance past that delay** (`vi.useFakeTimers()` + `vi.advanceTimersByTimeAsync(...)`) — a synchronous assertion right after triggering the delayed path proves nothing, since the delayed effect hasn't had a chance to fire either way. This exact test-quality gap shipped once in F3 (a drag-listener-leak regression test that would have passed identically against the bug it claimed to catch) before being caught and fixed. When writing a regression test for "X doesn't happen after Y," always ask what timing window X's side effect actually needs, and make sure the test's assertion happens after that window, not before it.

## Known cross-effects / risks

- **`SUPPORTED_EXTENSIONS` (Electron) and `EXTRACTOR_SPECS` (backend Python) are two independent lists with the same intent** — nothing enforces they stay in sync. Already caught one real drift during F1 (`.edf` was missing from the Electron list despite being a live, `pyedflib`-backed extractor). Worth a shared source of truth (e.g. the backend exposing its supported extensions via an endpoint) if this drifts again.
- **Real device/file testing (Windows, real `.adicht` files) is explicitly deferred** — per direct user instruction, not part of this build's verification loop. Everything is verified via Vitest + mocked `fetch` + `svelte-check`, not a real backend or real hardware.
- **`ImportScreen` has zero `tokens.css` styling** — plain unstyled `div`/`ul`/`li`. Deliberately deferred by F2's final review (judged optional/non-blocking, not a functional defect) rather than scope-creeping a fix wave. Needs a styling pass before this is the first thing a real user sees; not yet scheduled into F3-F5.
- **Stop only stops the queue from advancing, not the in-flight network request** — clicking Stop while a file is mid-`detectBeats` call cannot abort that specific HTTP request (browsers/fetch don't make this free without an `AbortController`, which wasn't wired in). This matches the workflow spec's actual requirement ("let the in-flight file finish") so it's not a defect, just worth knowing if a future "abort mid-request" requirement ever appears.
- **Bad-data marks render as a proportional strip below the graph, positioned against the FULL file extent** — not a canvas overlay synced to pan/zoom. This loses informational value exactly when zoomed in: a technician looking at a narrow time window has no indicator of whether the currently-visible range overlaps a mark without leaving the zoomed view. Explicitly parked by F3's final review as a real but larger-scope UX gap (would need a live viewport-position indicator on the strip, updated on the same debounce schedule as everything else) rather than folded into a fix wave. Marks themselves are still added/removed correctly; only the always-zoomed-out visual context is weak.
- **Beat marker rendering (`buildBeatAlignedData`) keeps only `ts`/`r_amplitude` per beat** — `rr`, `hr`, and all 7 arrhythmia category columns are discarded after the merge, and the raw `WindowBeat[]` from `getBeatsWindow` isn't retained anywhere on component state. F4 ("per-beat category list, confirm/reject/reassign") needs exactly this data keyed back from a click, plus click-vs-drag disambiguation (currently every `mousedown` unconditionally starts a pan or bad-data-mark drag — there's no hit-testing against individual beats at all). This is real re-architecture work at F3's exact rendering seam, explicitly deferred to be designed as part of F4 rather than retrofitted speculatively in F3.
- **Marker colors (arrhythmia/normal/not-yet-evaluated) are resolved from CSS custom properties once at component mount**, not reactively — if the OS theme changes while the app is open, canvas-rendered markers won't follow along (CSS-driven elements would, automatically, via the cascade). No in-app theme toggle exists anywhere in the codebase, so this is low-risk in practice; noted for whoever eventually adds one.
- **Sequential (not concurrent) fetching**: `EcgGraph` awaits `getChannelWindow` before starting `getBeatsWindow`, on every pan/zoom debounce tick — doubling round-trip latency versus `Promise.all`. Deliberate, for deterministic test ordering; revisit if real-world panning ever feels sluggish.
